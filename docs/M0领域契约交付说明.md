# 未见 M0 领域契约交付说明

> 完成日期：2026-10-15  
> 当前状态：已完成并通过后端、前端与真实 MySQL 验证

## 1. M0 的目标

M0 的目标不是继续增加产品页面，而是冻结后续开发共同依赖的领域语言、状态边界、接口字段和数据库结构，避免前端、后端与 PRD 分别使用不同概念。

本阶段围绕一条核心原则展开：

> 状态机只管理相遇是否完成；事件记录呈现生命体如何相处；真人决定关系是否开始。

因此，系统不再通过固定状态机把两个生命体自动推进为“注意、共历、在意、连接候选”，也不再让大模型为真人关系作出情感结论。

## 2. 本阶段冻结的领域对象

### 2.1 User

真实用户主体，拥有数据授权、社交意愿和真人连接的最终决定权。

### 2.2 Lifeform

用户养成的生命体。生命体可以在授权范围内探索问题和参与共同事件，但不能代表用户作出真人承诺或连接决定。

### 2.3 Evidence

用于形成候选理解的原始证据，包括应用内输入、理解校准以及经过授权的平台导入快照。

### 2.4 Understanding

生命体对用户形成的可解释理解。每条理解必须保留来源、置信度、状态和社交推荐授权。

### 2.5 Encounter

两个生命体围绕一个共同事件进行的一次有界互动。一次相遇可以完成、无效、失败或因一方离开而结束。

相遇只记录发生过程，不承载双方亲密程度。

### 2.6 Relationship

当前代码保留 `Relationship` 作为关系幕布的成对读模型，但它不再表示情感等级，只记录这一对生命体是否仍可继续探索，以及已经发生的相处事实。

### 2.7 UserDecision

用户看完相遇后作出的私密决定。双方邀请以前，一方不能读取另一方的决定。

### 2.8 Connection

双方用户分别发出邀请后建立的真人沟通许可。单方邀请不能开启聊天。

### 2.9 Message

真人连接建立后的文字消息。生命体不会替用户发送第一句话。

## 3. 状态契约

### 3.1 相遇状态

| 状态 | 含义 |
|---|---|
| `queued` | 已进入队列，尚未执行 |
| `running` | 两个生命体正在执行有限互动 |
| `completed` | 相遇正常完成 |
| `invalid` | 没有形成有效互动，但保留审计记录 |
| `left` | 一方主动离开 |
| `failed` | 执行失败 |
| `discarded` | 因授权变化、幂等冲突或调度规则被丢弃 |

合法迁移为：

```text
queued → running / discarded
running → completed / invalid / left / failed / discarded
```

所有终态均不能重新进入 `running`。

### 3.2 成对探索状态

| 状态 | 含义 |
|---|---|
| `active` | 这一对生命体仍可以继续探索 |
| `ended` | 用户已经结束这段探索 |
| `blocked` | 一方已经屏蔽，不能再次配对 |

该状态不表达喜欢、在意、亲密或匹配程度。

### 3.3 用户私密决定

| 决定 | 含义 |
|---|---|
| `observe_again` | 再观察或再经历一次 |
| `invite` | 希望认识对方真人 |
| `distance` | 保持距离，但暂不永久结束 |
| `end` | 结束这段探索 |
| `block` | 屏蔽并禁止再次匹配 |

### 3.4 真人连接状态

| 状态 | 含义 |
|---|---|
| `waiting` | 尚未获得双方邀请 |
| `mutual_accepted` | 双方都已邀请，允许创建真人频道 |
| `active` | 真人交流已经开启 |
| `ended` | 真人连接已经结束 |

连接状态不能从 `waiting` 直接进入 `active`，必须先确认双方邀请。

## 4. 相处过程的记录方式

系统不再维护情感阶段，而是记录可以从实际事件回放的事实：

- 双方讨论了什么问题；
- 每一轮由哪个生命体行动；
- 采取了靠近、观察、回应、合作、回避还是离开；
- 在哪里产生明确分歧；
- 是否发生误解和修正；
- 是否尊重对方边界；
- 是否愿意继续本次互动；
- 哪些问题仍未解决。

关系幕布只能对这些真实事件进行组织和摘要，不能增加没有发生过的剧情，也不能把模型语言解释为真人情感或承诺。

## 5. 数据库迁移

当前 Alembic migration head：

```text
0003_m0_encounter_count
```

### 5.1 `0002_m0_domain_contract`

该迁移完成以下变更：

- 将旧的关系情感阶段迁移为 `active / ended / blocked`；
- 将 `current_stage` 重命名为 `status`；
- 将关系事件中的 `previous_stage / proposed_stage / committed_stage` 改为对应的 `status` 字段；
- 将连接状态统一为 `waiting / mutual_accepted / active / ended`；
- 新增 `encounter_decisions`；
- 新增 `messages`；
- 保留已有相遇、共同经历和审计事件。

### 5.2 `0003_m0_encounter_count`

该迁移新增独立的 `encounter_count` 字段。

相遇次数不能复用 `projection_version`：后续用户决定、幕布更新或其他投影变化也可能增加版本号，但这些变化不代表又发生了一次相遇。

迁移已在真实 MySQL 上执行，并通过实际相遇行数比对验证。

## 7. 对外领域契约

新增接口：

```http
GET /api/v1/meta/domain-contract
```

该接口由运行时枚举和当前岛屿 fixture 直接生成，返回：

- 契约版本；
- 三座岛的规范 ID；
- 相遇状态；
- 生命体事件动作；
- 成对探索状态；
- 用户私密决定；
- 真人连接状态。

前端和后续客户端可以据此检查自己使用的枚举是否与后端一致。

## 8. 前端调整

前端已经移除以下情感阶段：

```text
未相识 / 注意 / 共历 / 在意 / 连接候选 / 停滞 / 保持距离
```

关系页面改为展示：

- 可以继续观察；
- 探索已经结束；
- 不再相遇；
- 最近的相处记录；
- 这一幕留下了什么；
- 相处事实不等于真人情感。

这使页面表达与新的领域契约保持一致。

> 用户看到的不是 AI 宣布“适合的人”，而是一个经过授权的生命体如何面对另一个真实差异。用户根据相处证据决定是否认识。

## 13. 下一阶段建议

下一阶段进入 M1，优先打通：

```text
Evidence
→ Candidate Understanding
→ 用户校准
→ AgentContextSnapshot
→ 岛屿选择与下一步行动
```

M1 的完成标准应当是：用户修改一条候选理解或其社交授权后，系统生成新的上下文快照，并在下一次决策中产生可以解释和测试的不同结果。
