# M2：相遇召回与配对

## 已交付闭环

用户设置探索边界 → manual/cron tick 读取当前授权 → 有界召回 → 确定性配对 → 保存双方社交快照 → 执行预设岛屿事件 → 双方查看共同经历 → 各自记录是否继续的决定。

这里的“真实配对”指真实用户创建的生命体参与选择，不代表已经使用大模型生成独立对话。事件仍标记为 fixture，页面明确展示“预设事件回放”。

## 规则

1. 用户可暂停相遇、修改社交节奏、排除议题；默认不跨岛、不匹配演示伙伴。
2. 暂停、观察优先、授权不足、忙碌、冷却、议题排除、保持距离、结束或屏蔽均为硬限制，不会被高分抵消。
3. 优先同岛与未曾相遇的对象。仅在明确许可且授权议题相关时考虑跨岛；初筛上限 120，最终候选上限 30。
4. 排序依据共同关注、同岛、社交节奏、等待和重复经历；使用固定种子打破平局。不从收藏或模糊文本臆造立场距离。
5. 提交前重新检查双方条件，保存双方不可变社交上下文快照。没有候选时返回正常等待，不用演示身份兜底。
6. 相遇后参与者冷却 10 分钟，同一对冷却 24 小时；保持距离 48 小时，结束或屏蔽持续抑制，后续较弱决定不会解除它。
7. “想再看看”和“邀请认识”只记录本人意愿，不自动开启真人聊天；另一方接口不会返回私密决定或候选池。

## 持久化与调度

迁移头为 `0006_m2_matching`。新增 `exploration_states`、`pair_exclusions`、`private_encounter_decisions`、`matching_guard`；tick 与相遇保存匹配解释。候选审计保存在内部数据中，不作为普通用户列表公开。

manual 与 cron 共用同一执行器，使用数据库事务保护并发占用。失败整体回滚；同步 fixture 事务中不调用外部服务。未来异步生成须先实施租约方案，见 ADR 0003。

前端新增探索设置、等待/冷却解释、真实相遇来源说明和私密决定。通信仍为 HTTP 请求与任务状态轮询，没有引入 SSE 或 WebSocket。

## 试测前边界

当前仍使用路径中的 user_id 做视角校验，正式开放前必须接入登录身份并替换客户端自报身份。边界检查仅覆盖已结构化的参与许可和排除议题，不宣称能够自动识别所有自由文本冲突。M3 再实现双方独立、可失败的真实交互；真人双向同意与聊天不在本次交付范围。
